## 2. 具体问题

### R01：任务中心缺少任务归属和模块权限隔离

**位置：** [router.py:388](../mtbots/router.py#L388)、[router.py:540](../mtbots/router.py#L540)、[jobs.py:62](../mtbots/jobs.py#L62)、[jobs.py:201](../mtbots/jobs.py#L201)。

`jobs_panel` 只检查用户是否在白名单，直接使用全局 `running()` 和 `render()`。任务模型保存 `chat_id`，但没有保存发起人 `user_id`，展示也没有按会话或模块权限过滤。

**触发与影响：**

- 普通 `user` 没有 Docker 权限，仍能看到 Docker 项目名和运行输出摘要。
- 私聊或群聊 A 打开任务中心，能看到会话 B 的任务。
- 取消只比较任务与当前会话的 `chat_id`；同一群里的其他白名单用户可取消管理员发起的 Docker 任务。

**验证：** 无 Docker 权限用户看到指定 Docker 任务标题；同群用户取消成功，两条路径均已复现。

**建议：** 增加任务发起人字段；展示、按钮生成和取消分别检查归属与模块权限。管理员全局查看或取消权限应采用明确策略。

**建议回归场景：** 跨私聊不可见；无 Docker 权限用户不可见 Docker 任务；同群其他用户不可取消；管理员行为符合既定策略。

### R02：日志脱敏在格式化前执行，漏掉异常对象与数字参数

**位置：** [logging_setup.py:67](../mtbots/logging_setup.py#L67)、[logging_setup.py:96](../mtbots/logging_setup.py#L96)。

过滤器处理 `record.msg` 和参数时，仅对字符串参数执行脱敏。异常对象和整数保留原样，随后 Formatter 才将其转换为文本。

例如 `log.warning("请求失败：%s", exc)` 中，异常对象携带的敏感内容可以绕过正则脱敏和已知 Token 替换；`log.info("user=%s chat=%s", user_id, chat_id)` 中，数字 ID 没有经过完整文本的 ID 正则处理。

**验证：** 使用合成敏感标记的异常对象和合成 ID，输出中仍包含原值。未使用实际凭据。

**建议：** 先取得 `record.getMessage()`，对完整消息进行正则脱敏和已知 Token 替换，然后设置 `record.msg` 并清空 `record.args`；保留异常栈的独立脱敏逻辑。异常对象、嵌套参数、数字参数和多 handler 场景应纳入回归验证。

### R03：Docker 输出只有 HTML 转义，没有敏感信息脱敏

**位置：** [compose.py:1175](../mtbots/features/docker/compose.py#L1175)、[compose.py:1202](../mtbots/features/docker/compose.py#L1202)、[handlers.py:199](../mtbots/features/docker/handlers.py#L199)、[handlers.py:321](../mtbots/features/docker/handlers.py#L321)。

命令 stdout/stderr 被直接用于 Telegram 进度消息、结果尾部、任务详情和失败面板。`esc()` 仅转义 HTML，不会隐藏密码、Token 或认证 URL。日志 handler 的过滤器不会保护这些消息出口。

**触发与影响：** 命令输出包含认证信息时，信息进入聊天和内存任务表；结合 R01，还可能被其他白名单用户看到。

**验证：** 合成的 `password=…` 字段完整进入消息编辑参数。

**建议：** 在输出进入预览、结果、任务详情和失败摘要前执行统一脱敏，再做 HTML 转义。需要明确支持的敏感字段和已知秘密替换规则，不能认为少量正则能覆盖任意秘密格式。

**记录现状：** Docker 模块没有主动持久化完整 stdout/stderr；主要保存在有限长度的内存缓冲区和聊天消息中，普通日志记录的是部分摘要。

### R04：非法角色配置回退到最高权限

**位置：** [acl.py:60](../mtbots/acl.py#L60)、[acl.py:69](../mtbots/acl.py#L69)、[config.py:154](../mtbots/config.py#L154)。

非法默认角色被替换为 `owner`。单个用户的非法角色被忽略后，使用默认角色，而默认值也是 `owner`。

**触发与影响：** 将 `user` 写成 `usr`，或者将默认角色写成 `admn`，可能使原本应受限的白名单用户获得 Docker 管理权限。

**验证：** 非法用户角色解析为 `owner`，`acl.can(uid, "docker")` 返回 True。

**建议：** 对非法默认角色及用户角色显式报配置错误并阻止启动，避免静默提升权限。

### R05：LitePan 按盘筛选忽略 parse_ok

**位置：** [discovery.py:134](../mtbots/features/litepan/discovery.py#L134)、[discovery.py:194](../mtbots/features/litepan/discovery.py#L194)、[handlers.py:725](../mtbots/features/litepan/handlers.py#L725)。

发现规则时，代码用 `parse_ok` 判断是否所有动作均成功解析，仅将安全单盘规则加入 `by_account`。但是 `account_rules()` 重新遍历全部规则，只检查已解析账号列表长度，没有检查 `parse_ok`。

**触发与影响：** 规则包含盘 A 的有效任务以及未知动作或不存在的任务时，`/refresh A` 仍会选择并执行整条规则，超出按盘选择所能确认的范围。

**验证：** 一个有效 STRM 任务与一个不存在的 organize 任务组成规则；`by_account` 为空，但 `account_rules("A")` 返回该规则。

**建议：** 以规则 ID 保存完整解析成功的单盘规则索引，按盘执行只使用该索引。不能仅按事件过滤，因为同一事件可对应不同规则。

### R06：LitePan 回执去重缺少实例与接收会话

**位置：** [handlers.py:74](../mtbots/features/litepan/handlers.py#L74)、[handlers.py:602](../mtbots/features/litepan/handlers.py#L602)。

`receipted_runs` 是模块共享状态，去重键只有 `(rule_id, run_id)`。

**触发与影响：** 两个实例返回相同规则 ID 和运行 ID 时，第二个实例的成功结果会被跳过，最终报超时；多个接收会话也可能互相吞回执。

**验证：** 两个假实例均返回成功运行，结果为第一项完成、第二项超时失败。

**建议：** 去重键包含稳定实例标识、接收会话和运行 ID；为去重记录增加清理策略。同规则并发触发的运行匹配也值得后续核对，但本报告未验证真实接口的运行 ID 返回合同。

### R07：Cline 多词别名删除只取第一个参数

**位置：** [core.py:545](../mtbots/features/cline/core.py#L545)、[handlers.py:448](../mtbots/features/cline/handlers.py#L448)。

添加允许带空格的别名，删除却只取 `context.args[0]`。

**触发与影响：** `/delkey Cline 01` 删除目标为 `Cline`，而非 `Cline 01`。两个别名同时存在时会删除错误的绑定。

**验证：** 内存替身收到的删除目标为 `Cline`，多词别名保留。

**建议：** 拼接全部别名参数，复用添加时的别名规范化和校验。回归场景必须包含短别名与多词别名同时存在。

### R08：Cline Key 更新与额度查询存在缓存回写竞态

**位置：** [handlers.py:405](../mtbots/features/cline/handlers.py#L405)、[handlers.py:225](../mtbots/features/cline/handlers.py#L225)、[handlers.py:674](../mtbots/features/cline/handlers.py#L674)。

添加或替换 Key 后会清空快照，但查询使用独立查询锁。旧查询先读取 Key，等待网络后无条件写入快照，没有核对绑定是否已变化。

**触发与影响：** 旧查询等待期间更换同名 Key，旧结果随后重新进入缓存，首页可能显示旧 Key 额度。

**验证：** 挂起旧查询、更换同名 Key 并清缓存、释放查询后，旧快照重新出现。

**建议：** 为 Key 集合增加版本号或指纹；回写缓存和面板前核对版本，丢弃过期结果，不必在网络等待期间持有存储锁。

### R09：首页渲染失败后刷新占位未释放

**位置：** [router.py:293](../mtbots/router.py#L293)、[router.py:298](../mtbots/router.py#L298)。

首页先占用刷新槽位，然后渲染面板，最后启动后台刷新。渲染抛异常时，后台任务没有启动，也没有释放 `busy`。

**触发与影响：** 首页发送失败后，相应用户和模块的刷新持续被去重逻辑跳过；强制刷新也不能解除该状态，通常需重启进程。

**验证：** 模拟渲染异常后，刷新调用次数为 0，刷新槽位仍为 `busy=True`。

**建议：** 渲染失败路径释放已声明的槽位，确保占位由实际后台任务接管或及时退回。

### R10：多主机全量升级预检错误

**位置：** [handlers.py:1185](../mtbots/features/docker/handlers.py#L1185)、[handlers.py:1195](../mtbots/features/docker/handlers.py#L1195)、[handlers.py:1292](../mtbots/features/docker/handlers.py#L1292)。

全量升级预热各主机探测后，最终检查 `target_host or state.local_host`；全量模式中 `target_host=None`，因此检查本机。

**触发与影响：**

- 本机缺 Compose、远端有可升级项目时，整批被误阻断。
- 本机正常、某远端缺 Compose 时，可能在该远端构建命令时抛异常，外层异常处理终止整批，后续项目不再执行。

**验证边界：** 静态代码路径确认，未执行真实升级。

**建议：** 按目标主机预检；逐项记录失败，避免单台不可用主机中断其他主机。是否对部分失败继续执行，需要明确批量操作策略。

### R11：LitePan 非法配置形状中断加载

**位置：** [config.py:152](../mtbots/features/litepan/config.py#L152)、[config.py:208](../mtbots/features/litepan/config.py#L208)、[config.py:331](../mtbots/features/litepan/config.py#L331)。

条目加载只捕获 `ConfigError`，但非对象用户条目、布尔型 `chat_ids`、非对象 `drives` 会产生 `AttributeError` 或 `TypeError`。

**触发与影响：** 例如用户数组中先出现 null，后有合法条目，不能按预期跳过坏条目继续加载，可能使模块初始化或配置加载失败。

**验证：** 使用内存配置字典验证异常类型，未读取真实配置。

**建议：** 校验用户条目、chat_ids 和 drives 的类型，将形状错误统一转换为 `ConfigError`，保留逐条跳过机制。

### R12：JsonStore 写盘失败不回滚内存

**位置：** [store.py:122](../mtbots/store.py#L122)。

`mutate()` 直接修改当前 `_data`，然后保存；保存失败时内存仍包含新内容。mutator 修改一部分后抛异常也没有事务回滚。

**验证：** 模拟磁盘写入失败后，内存中的字段仍为修改后的值。

**影响边界：** Cline 的常规后续 keys/add/delete 操作会重新读盘，因此不能断言该模块会持续使用未落盘数据；底层存储 API 的一致性问题仍然存在。

**建议：** 在副本上执行修改并保存，成功后提交内存状态；失败时保留原状态。避免在没有需求的情况下引入复杂事务框架。

### R13：Docker 拉取失败消息在下一次重试前未清理

**位置：** [compose.py:1215](../mtbots/features/docker/compose.py#L1215)、[handlers.py:861](../mtbots/features/docker/handlers.py#L861)、[handlers.py:1000](../mtbots/features/docker/handlers.py#L1000)、[test_docker_module.py:874](../tests/test_docker_module.py#L874)。

`run_command_with_feedback()` 在命令成功时，因 `delete_on_success=True` 删除过程消息；命令失败时只把同一条消息编辑为失败状态并保留。下一次项目或服务升级会直接创建新的过程消息，没有记录并清理上一次对应的失败消息。

**触发与影响：**

1. 第一次 `pull` 失败，聊天中保留失败详情；
2. 用户再次确认同一项目或服务升级；
3. 新的拉取过程消息被创建，但旧失败消息不会自动删除；
4. 多次重试后，聊天中会累积多条失败消息，旧错误容易与当前执行混淆。

项目升级和服务升级都存在相同路径。现有测试还将“失败消息必须保留”作为预期，只覆盖单次执行，没有覆盖下一次重试前的清理行为。

**建议：** 为会话、项目、服务和主机记录上一次失败过程消息。新任务目标确认后，先尝试删除对应旧消息，再创建新的过程消息；删除失败只记日志，不阻断新任务。成功、取消和新任务创建后同步清理过期引用，避免误删其他项目或其他模块的消息。

**建议回归场景：** 第一次失败消息保留；第二次同目标重试前删除第一次失败消息；第二次失败只保留第二次失败消息；不同服务、不同主机互不删除；删除 Telegram 消息失败时升级仍继续。

### R14：远端接入脚本目标路径未安全传递

**位置：** [setup-remote-host.sh:465](../scripts/setup-remote-host.sh#L465)。

`GUARD_DEST` 通过字符串拼接并嵌入远端 shell 命令，没有安全处理单引号及 shell 元字符。

**触发与影响：** 路径包含特殊字符时会破坏参数解析，构造输入也可能形成额外命令。当前输入来自操作者本人，没有确认低信任输入来源，因此列为参数可靠性问题，不按已证实的高危外部攻击入口处理。

**建议：** 使用可靠的远端参数传递方式，或严格限制目标绝对路径的字符集合。

## 3. 日志与操作记录改进

### 3.1 统一操作关联字段

[任务结束日志](../mtbots/jobs.py#L145)没有任务 ID，部分 Docker 操作日志仅包含项目名。建议统一记录：

- `job_id`、模块、动作和目标；
- 操作者及会话的稳定脱敏标识；
- 开始时间、最终结果、耗时、命令阶段和退出码；
- 脱敏后的失败摘要。

脱敏后仍应能关联同一次操作。不要简单删除所有身份信息而使追踪失效，也不要为审计默认保存原始 Telegram ID 或秘密。

### 3.2 显式设置日志文件权限

[RotatingFileHandler 初始化](../mtbots/logging_setup.py#L166)没有显式设置权限，实际权限取决于 umask；本次未读取现有日志或核验实际权限。

建议日志目录使用 `0700`，当前和滚动日志使用 `0600`，同时覆盖已有文件和轮转后的文件。

### 3.3 持久化必要结果，限制输出体积

完整 Docker stdout/stderr 未主动落盘；任务中心内存表重启即清空。建议持久化脱敏后的阶段、退出码和失败摘要，保留明确的轮转与容量上限，无需默认保存大量镜像拉取进度。

### 3.4 脱敏测试应覆盖实际出口

建议验证格式化后的日志、异常栈、异常对象参数、整数 ID、已知秘密替换、Docker HTML 消息及纯文本降级消息。仅测试 `redact()` 函数本身不足以证明出口受到保护。

## 4. 有实际收益的优化

- **缓存提交增加版本检查：** 优先解决 R08，避免查询完成后覆盖新状态；不建议为了规避竞态而在网络等待期间锁住 Key 修改。
